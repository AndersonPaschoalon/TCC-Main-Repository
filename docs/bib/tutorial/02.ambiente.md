# Parte 2: Preparando o ambiente

**Objetivo desta parte:** confirmar que o sistema reconhece o acelerador (GPU, se houver), levantar os dados da máquina, instalar o Ansible e criar a pasta do projeto que guarda a infraestrutura. Nenhum serviço do Slurm é instalado aqui.

**Pré-requisitos:**
- Linux baseado em Ubuntu 24.04 (ou derivado), com terminal e permissão `sudo`.
- Opcional: uma GPU. Sem ela, ignore as verificações que tratam de GPU e faça apenas o levantamento de CPU e memória.

---

## Como ler esta parte

Ferramentas mudam. Rótulos de saída mudam entre versões de driver, nomes de pacote mudam entre versões do sistema, e opções de comando são renomeadas. Por isso, a apostila segue duas regras:

1. **Conceitos antes de comandos.** Antes de cada comando, está explicado o que se quer descobrir. Se o comando mudar, o conceito continua válido.
2. **Use a própria ferramenta para descobrir.** Todo comando aceita `--help`, `man <comando>` ou `ansible-doc <módulo>`. Esses são os caminhos de referência atualizados.

## 2.1 Verificando o acelerador (GPU)

A verificação de uma GPU tem três camadas. Cada uma responde a uma pergunta diferente:

| Camada | Pergunta | Ferramenta típica |
|---|---|---|
| **Hardware** | A placa está presente no barramento da máquina? | `lspci` |
| **Driver** | O módulo do kernel que se comunica com a placa está carregado? | `lsmod` |
| **Ferramenta de estado** | A placa responde a consultas? | `nvidia-smi` (NVIDIA), `rocm-smi` (AMD) |

Esse modelo de três camadas vale para qualquer fabricante. Se a placa mudar, a lógica é a mesma. Só o nome das ferramentas muda.

### Camada 1: hardware

```bash
lspci | grep -iE 'vga|3d|display'
```

A linha lista os dispositivos gráficos no barramento PCI. Você deve ver o nome do fabricante e do modelo. Em máquinas com gráficos híbridos (um integrado e uma placa dedicada), as duas aparecem aqui, e isso é normal.

Se `lspci` não estiver disponível:

```bash
sudo apt install -y pciutils
```

### Camada 2: driver

Para placas NVIDIA:

```bash
lsmod | grep -i '^nvidia'
```

Para placas AMD, o módulo é `amdgpu`. Se a linha aparecer, o módulo está carregado. Se não aparecer, o driver não está ativo, e a camada 3 deve falhar.

### Camada 3: ferramenta de estado

```bash
nvidia-smi
```

Se a ferramenta responder com uma tabela, a GPU está operacional. Para identificar os campos da saída, consulte o item 1.3 da introdução. Os rótulos mudam entre versões, então leia o conceito e não o texto.

Para o nome completo do modelo, sem truncamento:

```bash
nvidia-smi -L
```

Para extrair valores específicos de forma legível por máquina:

```bash
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv
```

Se alguma opção não existir na sua versão, consulte `nvidia-smi --help` e procure a equivalente.

### Registro do ambiente

Anote os valores em um arquivo dentro do projeto, para não depender da memória. Isso também permite que qualquer pessoa que reproduza a configuração saiba em qual hardware ela foi testada.

O arquivo `docs/ambiente-host.md` é criado, vazio, pelo script da seção 2.4, junto com a pasta do projeto. Até lá, anote os valores à parte e transfira-os depois para o arquivo, com um registro por máquina no formato abaixo:

```markdown
# Ambiente do host

| Item | Valor |
|---|---|
| Função da máquina | a preencher (ex.: controlador, nó de computação, desenvolvimento) |
| Hostname curto (`hostname -s`) | a preencher |
| Distribuição (`/etc/os-release`) | a preencher |
| Tipo de máquina (notebook ou desktop) | a preencher |
| GPU (`nvidia-smi -L`) | a preencher ou "sem GPU" |
| Memória de vídeo | a preencher |
| Versão do driver | a preencher |
| Versão CUDA suportada | a preencher |
| Secure Boot (`mokutil --sb-state`) | a preencher |
| CPUs (`nproc`) | a preencher |
| Memória total (`free -m`) | a preencher |
```

### Notas sobre notebook

Se a máquina for um notebook, o limite de consumo da placa aparece na saída do `nvidia-smi` (por exemplo, 80 W). Isso traz consequências para um nó de computação, que um servidor não teria:

- **Suspensão e tampa fechada:** se a máquina suspender, o nó deixa de responder e o Slurm o marca como indisponível.
- **Energia:** rodar cargas pesadas na bateria reduz desempenho e pode desligar a máquina.
- **Temperatura:** cargas longas fazem a GPU reduzir a frequência (*thermal throttling*), o que afeta medições de desempenho.
- **Gráficos híbridos:** a placa dedicada pode desligar quando não está em uso. Isso é normal e explica variações no tempo de inicialização.

Essas condições não impedem o uso da apostila, mas devem ser registradas, porque afetam a interpretação de resultados.

### Secure Boot

O Secure Boot pode impedir o carregamento de módulos do kernel que não estejam assinados, como o driver de algumas GPUs. Verifique o estado:

```bash
mokutil --sb-state
```

Se o Secure Boot estiver ativo e a camada 2 ou a camada 3 falharem, há duas saídas: desativar o Secure Boot na BIOS/UEFI, ou registrar uma chave de assinatura para o módulo (o Gerenciador de Drivers do Linux Mint orienta esse processo). Anote a escolha no registro do ambiente.

Se o driver não estiver instalado, o caminho mais direto no Ubuntu e derivados é:

```bash
ubuntu-drivers devices          # lista os drivers recomendados para a placa
sudo ubuntu-drivers install     # instala o recomendado
sudo reboot
```

No Linux Mint, o Gerenciador de Drivers gráfico faz a mesma coisa.

> **Referência:** NVIDIA. *nvidia-smi: NVIDIA System Management Interface*. Guia do usuário, disponível em docs.nvidia.com. Use a versão do guia correspondente ao driver instalado.
> **Referência:** Gregg, B. *Systems Performance: Enterprise and the Cloud*. Addison-Wesley. Capítulos sobre inventário e observação de hardware. (Verifique a edição antes de citar.)

## 2.2 Levantando os dados de hardware

O Slurm precisa saber quantas CPUs e quanta memória cada nó tem. Esses valores devem ser reais. Se forem maiores que os da máquina, o Slurm marca o nó como indisponível, o que aparece na validação da Parte 9.

Comandos estáveis há muitos anos:

```bash
hostname -s       # nome curto da máquina
nproc             # número de processadores lógicos disponíveis
free -m           # memória em megabytes
```

Na saída de `free -m`, use o valor da coluna `total`, na linha `Mem:`, e registre no arquivo de ambiente.

Esse valor serve como estimativa inicial, não como valor final. A memória que o Slurm detecta costuma ser um pouco menor que o total do `free -m`, porque parte dela é reservada pelo kernel. Se a memória declarada ao Slurm for maior que a detectada, o nó é marcado como indisponível. Por isso, ao declarar a memória ao Slurm (Parte 3), use um valor com margem, por exemplo 5% abaixo do total. A referência final é o comando `slurmd -C`, apresentado a seguir.

Para a visão completa da CPU:

```bash
lscpu | head -20
```

### Sobre `slurmd -C`

`slurmd -C` mostra a configuração que o Slurm enxerga na máquina. O comando só existe depois da instalação do pacote do Slurm, na Parte 4. Até lá, use `nproc` e `free -m`. Na Parte 4, os valores de `nproc` e `free -m` devem ser comparados com os de `slurmd -C`. Em caso de diferença, prevalece o valor de `slurmd -C`, em especial o campo `RealMemory`.

> **Referência:** Kerrisk, M. *The Linux Programming Interface*. No Starch Press. Capítulo sobre informações do sistema, que explica a origem desses valores no diretório `/proc`. (Verifique a edição antes de citar.)

## 2.3 Instalando o Ansible

O Ansible está nos repositórios oficiais do Ubuntu:

```bash
sudo apt update
sudo apt install -y ansible
```

Confirme a versão:

```bash
ansible --version
```

Em `ansible --version`, observe duas linhas:

- `ansible [core ...]`: versão do núcleo.
- `config file = ...`: arquivo de configuração em uso. Ele ainda não é o do projeto. Isso muda na Parte 3.

> **Dica:** se um pacote não for encontrado, use `apt search <termo>` para descobrir o nome correto na sua versão da distribuição. Nomes de pacote mudam com o tempo.

> **Referência:** Ansible. *Installing Ansible*. docs.ansible.com. Guia oficial de instalação, com instruções por distribuição.

## 2.4 Criando a estrutura do projeto

A infraestrutura é mantida em uma pasta que este tutorial chama de `slurm-lab`. Você pode criar a estrutura à mão, mas o script abaixo faz isso de forma repetível. Ele segue a mesma lógica da IaC: o que é criado está descrito em um arquivo.

Crie o arquivo `bootstrap-estrutura.sh` em qualquer pasta, com o conteúdo abaixo:

```bash
#!/usr/bin/env bash
# Cria a estrutura de pastas e arquivos vazios do projeto slurm-lab.
# Pode ser executado várias vezes: não sobrescreve arquivos existentes.
set -euo pipefail

PROJETO="slurm-lab"

mkdir -p "$PROJETO"/{inventory,group_vars,docs} \
         "$PROJETO"/roles/{base,munge,slurm}/{tasks,handlers} \
         "$PROJETO"/roles/slurm/templates

cd "$PROJETO"

# Cria arquivos vazios apenas se ainda não existirem.
touch -a ansible.cfg inventory/hosts.yml group_vars/all.yml site.yml docs/ambiente-host.md
for role in base munge slurm; do
  [ -f "roles/$role/tasks/main.yml" ] || echo "[]" > "roles/$role/tasks/main.yml"
done
[ -f roles/slurm/handlers/main.yml ] || echo "[]" > roles/slurm/handlers/main.yml

echo "Estrutura criada em ./$PROJETO"
```

O que o script faz:

- `set -euo pipefail`: interrompe o script na primeira falha, para não deixar a estrutura incompleta. É um padrão de scripts bash seguros.
- `mkdir -p ...`: cria todas as pastas de uma vez. A notação `{a,b}` é uma expansão do bash que gera `a` e `b`.
- `touch -a`: cria o arquivo se não existir, sem alterar o conteúdo se existir.
- `echo "[]" > ...`: cria os arquivos de tarefas como lista vazia. É YAML válido, e permite que o playbook passe na checagem de sintaxe antes de as tarefas serem escritas.

Execute:

```bash
chmod +x bootstrap-estrutura.sh
./bootstrap-estrutura.sh
cd slurm-lab
```

Confira a estrutura:

```bash
find . | sort
```

> **Recomendação:** mantenha a pasta `slurm-lab` sob controle de versão, com uma ferramenta como o Git, e registre uma versão a cada mudança relevante. Isso permite voltar a uma configuração que funcionava. O controle de versão não faz parte desta apostila, e nenhum passo depende dele.

> **Referência:** Shotts, W. *The Linux Command Line*. No Starch Press. Para o bash, incluindo `set -euo pipefail` e a expansão de chaves.
