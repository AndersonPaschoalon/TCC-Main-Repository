# 🛠️ SPEC-01: Provisionamento de Infraestrutura via IaC (Slurm Cluster)

## 1. Visão Geral e Objetivos
* **Objetivo**: Subir e configurar de forma automatizada, idempotente e reprodutível um cluster heterogêneo gerenciado pelo **Slurm Workload Manager**, equipado com aceleração por GPU, banco de dados para contabilização (*accounting*), priorização por *fair-share* e armazenamento compartilhado (NAS).
* **Tecnologia Principal de IaC**: Ansible.
* **Ambiente Alvo**: Linux Ubuntu 24.04 LTS (ou equivalente), com a mesma versão do Slurm em todos os nós.
* **Princípio Arquitetural**: O inventário do Ansible e as variáveis são a **única fonte da verdade** (*single source of truth*). NENHUM arquivo dentro de `/etc/slurm/` deve ser editado manualmente.

---

## 2. Componentes da Pilha Tecnológica (*Stack*)
1. **Sincronização de Relógio**: `chrony` (o munge rejeita credenciais quando os relógios dos nós divergem).
2. **Autenticação Inter-Nós**: `munge` (chave simétrica em `/etc/munge/munge.key`, idêntica em todos os nós).
3. **Gerenciador de Cargas (Slurm)**:
   * `slurmctld`: Daemon do nó controlador (fila central, prioridade e alocação).
   * `slurmd`: Daemon dos nós de computação (*workers*).
   * `slurmdbd`: Daemon de contabilidade de histórico, base do cálculo de *fair-share*.
4. **Banco de Dados**: MariaDB (armazenamento persistente de histórico para `slurmdbd`).
5. **Armazenamento Compartilhado**: NAS via NFS montado em `/mnt/nas` em todos os nós.
6. **Isolamento de Recursos**: Kernel `cgroups` (para delimitar CPUs, memória e GPUs por job).
7. **Usuários**: Contas Linux com UID/GID idênticos em todos os nós e associações correspondentes no `sacctmgr`.

---

## 3. Topologia e Grupos do Inventário

| Grupo | Hosts | Serviços |
|---|---|---|
| `controller` | 1 host | `slurmctld`, `slurmdbd`, MariaDB, comandos cliente |
| `compute` | \\(N\\) hosts | `slurmd`, GPUs |
| `all` | Todos | `chrony`, `munge`, usuários, cliente NFS |

O nome de cada host no inventário deve ser igual ao nome curto da máquina (`hostname -s`), pois é usado como `NodeName` no Slurm.

## 4. Estrutura do Repositório Ansible (`slurm-lab/`)

```text
slurm-lab/
├── ansible.cfg                 # inventory, playbook_dir, interpreter_python, vault_password_file
├── inventory/
│   └── hosts.yml               # Hosts e grupos (controller, compute)
├── group_vars/
│   └── all/
│       ├── main.yml            # Variáveis globais do cluster (seção 5.1)
│       └── vault.yml           # Segredos cifrados com Ansible Vault (seção 5.3)
├── host_vars/
│   └── <hostname>.yml          # Hardware de cada nó de computação (seção 5.2)
├── site.yml                    # Playbook principal de orquestração (seção 7)
└── roles/
    ├── base/                   # Pacotes, chrony, diretórios de estado e de log
    ├── users/                  # Usuários Linux com UID/GID fixos
    ├── munge/                  # Instalação da chave munge (Vault) e serviço
    ├── nfs_client/             # Montagem do NAS e pastas compartilhadas
    ├── mariadb/                # Banco slurm_acct_db e usuário do slurmdbd
    ├── slurmdbd/               # slurmdbd.conf e serviço slurmdbd
    ├── slurm/                  # slurm.conf, gres.conf, cgroup.conf; slurmctld/slurmd
    └── slurm_accounting/       # Cluster, contas e associações no sacctmgr
```

Configuração mínima do `ansible.cfg`:

```ini
[defaults]
inventory = inventory/hosts.yml
playbook_dir = .
interpreter_python = auto_silent
retry_files_enabled = False
vault_password_file = .vault_pass
```

O arquivo `.vault_pass` nunca é versionado (`.gitignore`).

## 5. Variáveis (Fonte Única da Verdade)

### 5.1. `group_vars/all/main.yml`
```yaml
cluster_name: mini-cluster
controller_host: ctl                 # nome curto do host do grupo controller

slurm_partition:
  name: lab
  default_time: "01:00:00"           # aplicado a jobs sem --time (necessário ao backfill)
  max_time: "2-00:00:00"

slurm_def_mem_per_cpu: 2000          # MB; evita que jobs sem --mem recebam a memória toda do nó

slurm_priority:
  decay_half_life: "7-0"             # meia-vida do uso histórico no fair-share
  weight_fairshare: 10000
  weight_age: 1000
  weight_job_size: 0
  weight_partition: 0
  weight_qos: 0
  max_age: "7-0"

nas:
  server: nas.lab.local
  export: /export/slurm
  mount_point: /mnt/nas
  dirs: [code, datasets, checkpoints, telemetry, logs]

slurm_account: lab
cluster_users:
  - { name: pesado_1, uid: 2001 }
  - { name: pesado_2, uid: 2002 }
  - { name: leve_1,   uid: 2003 }
  - { name: leve_2,   uid: 2004 }
  - { name: leve_3,   uid: 2005 }
```

### 5.2. `host_vars/<hostname>.yml` (um arquivo por nó de computação)
```yaml
cpus: 16
real_memory: 30000                   # MB, com margem abaixo do total; conferir com slurmd -C
gpu_count: 1                         # 0 para nós sem GPU
gpu_type: rtx3060                    # opcional; permite pedir --gres=gpu:rtx3060:1
gpu_device: /dev/nvidia0             # aceita faixa, ex.: /dev/nvidia[0-1]
```

Os valores são ilustrativos. `RealMemory` deve ser menor ou igual ao valor reportado por `slurmd -C` no próprio nó.

### 5.3. `group_vars/all/vault.yml` (cifrado com `ansible-vault`)
```yaml
vault_munge_key_b64: "<chave munge de 1024 bytes em base64>"
vault_slurmdbd_db_password: "<senha do usuário slurm no MariaDB>"
```

A chave munge é gerada **uma única vez**, fora do playbook, e guardada no Vault:

```bash
dd if=/dev/urandom bs=1 count=1024 2>/dev/null | base64 -w0
```

## 6. Requisitos de Configuração e Templates (Jinja2)

### 6.1. `slurm.conf.j2`
* **Identificação**:
  * `ClusterName={{ cluster_name }}`
  * `SlurmctldHost={{ controller_host }}`
  * `SlurmUser=slurm`
  * `StateSaveLocation=/var/spool/slurmctld`, `SlurmdSpoolDir=/var/spool/slurmd`
* **Autenticação**: `AuthType=auth/munge`.
* **Rastreamento de Processos e Isolamento** (pré-requisito do `cgroup.conf`):
  * `ProctrackType=proctrack/cgroup`
  * `TaskPlugin=task/cgroup,task/affinity`
* **Políticas do Escalonador**:
  * `SchedulerType=sched/backfill` (permite preenchimento de lacunas; depende de limites de tempo nos jobs ou de `DefaultTime` na partição).
  * `SelectType=select/cons_tres` (trata CPUs, memória e GPUs como recursos consumíveis).
  * `SelectTypeParameters=CR_Core_Memory` (aloca núcleos inteiros e contabiliza a memória pedida com `--mem`).
  * `DefMemPerCPU={{ slurm_def_mem_per_cpu }}`.
  * `GresTypes=gpu`.
* **Prioridade e *Fair-share***:
  * `PriorityType=priority/multifactor`
  * `PriorityDecayHalfLife={{ slurm_priority.decay_half_life }}`
  * `PriorityMaxAge={{ slurm_priority.max_age }}`
  * `PriorityWeightFairshare`, `PriorityWeightAge`, `PriorityWeightJobSize`, `PriorityWeightPartition`, `PriorityWeightQOS` a partir de `slurm_priority`.
* **Contabilidade**:
  * `AccountingStorageType=accounting_storage/slurmdbd`
  * `AccountingStorageHost={{ controller_host }}`
  * `AccountingStorageEnforce=associations` (somente usuários com associação no `sacctmgr` podem submeter jobs).
  * `AccountingStorageTRES=gres/gpu` (contabiliza GPUs no uso e, portanto, no *fair-share*).
  * `JobAcctGatherType=jobacct_gather/cgroup`
* **Retomada de Nós**: `ReturnToService=2` (ver Observação 4).
* **Topologia de Nós e Partição**: laço sobre `groups['compute']`. O campo `Gres` só é gerado para nós com GPU:
  ```jinja2
  {% for h in groups['compute'] %}
  NodeName={{ h }} CPUs={{ hostvars[h].cpus }} RealMemory={{ hostvars[h].real_memory }}{% if hostvars[h].gpu_count | default(0) > 0 %} Gres=gpu:{% if hostvars[h].gpu_type is defined %}{{ hostvars[h].gpu_type }}:{% endif %}{{ hostvars[h].gpu_count }}{% endif %} State=UNKNOWN
  {% endfor %}
  PartitionName={{ slurm_partition.name }} Nodes={{ groups['compute'] | join(',') }} Default=YES DefaultTime={{ slurm_partition.default_time }} MaxTime={{ slurm_partition.max_time }} State=UP
  ```

### 6.2. `gres.conf.j2`
* Linhas geradas apenas para nós com `gpu_count > 0`, mapeando explicitamente os dispositivos do sistema operacional:
  ```jinja2
  {% for h in groups['compute'] if hostvars[h].gpu_count | default(0) > 0 %}
  NodeName={{ h }} Name=gpu{% if hostvars[h].gpu_type is defined %} Type={{ hostvars[h].gpu_type }}{% endif %} File={{ hostvars[h].gpu_device }}
  {% endfor %}
  ```

### 6.3. `cgroup.conf.j2`
* Habilitar restrições rigorosas de isolamento de hardware por job:
  ```ini
  CgroupPlugin=autodetect
  ConstrainCores=yes
  ConstrainRAMSpace=yes
  ConstrainDevices=yes
  ```

### 6.4. `slurmdbd.conf.j2`
* Arquivo com dono `slurm` e permissão `0600` (contém senha):
  ```ini
  DbdHost={{ controller_host }}
  SlurmUser=slurm
  StorageType=accounting_storage/mysql
  StorageHost=localhost
  StorageLoc=slurm_acct_db
  StorageUser=slurm
  StoragePass={{ vault_slurmdbd_db_password }}
  LogFile=/var/log/slurm/slurmdbd.log
  PidFile=/run/slurmdbd.pid
  ```

### 6.5. Distribuição dos Arquivos
* `slurm.conf`, `gres.conf` e `cgroup.conf` são gerados **idênticos** em todos os nós (controlador e computação).
* `slurmdbd.conf` é gerado apenas no controlador.

## 7. Fluxo de Execução do Playbook (`site.yml`)

O playbook é dividido em *plays* por grupo, na ordem de dependência entre os serviços:

| Ordem | Hosts | Role | Responsabilidade |
|---|---|---|---|
| 1 | `all` | `base` | Instala pacotes via `apt` (`chrony`, `munge`, `slurm-client`, `nfs-common`; `slurmctld` e `slurmdbd` no controlador; `slurmd` nos nós de computação). Cria `/var/spool/slurmctld` (dono `slurm`), `/var/spool/slurmd` (dono `root`) e `/var/log/slurm`. |
| 2 | `all` | `users` | Cria os usuários de `cluster_users` com UID/GID fixos. |
| 3 | `all` | `munge` | Grava `munge.key` a partir de `vault_munge_key_b64` (permissão `0400`, dono `munge`) e garante o serviço ativo e habilitado no boot. |
| 4 | `all` | `nfs_client` | Monta `nas.server:nas.export` em `nas.mount_point` (persistente em `/etc/fstab`). Cria as pastas de `nas.dirs` uma única vez (`run_once`), com permissão de escrita para os usuários do cluster. |
| 5 | `controller` | `mariadb` | Instala MariaDB, cria o banco `slurm_acct_db` e o usuário `slurm` com a senha do Vault. Aplica os ajustes de InnoDB recomendados pela documentação do Slurm. |
| 6 | `controller` | `slurmdbd` | Renderiza `slurmdbd.conf` e garante `slurmdbd` ativo. |
| 7 | `controller` | `slurm_accounting` | Registra o cluster no `sacctmgr` (antes do primeiro início do `slurmctld`). |
| 8 | `all` | `slurm` | Renderiza `slurm.conf`, `gres.conf` e `cgroup.conf`. Garante `slurmctld` ativo no controlador e `slurmd` nos nós de computação. Notifica os *handlers* para reiniciar os serviços apenas se a configuração for alterada (*idempotência*). |
| 9 | `controller` | `slurm_accounting` | Cria a conta `slurm_account` e as associações de cada usuário de `cluster_users`. |

As tarefas de `sacctmgr` usam a opção `-i` (sem confirmação interativa) e verificam a existência do item antes de criá-lo, para que a segunda execução não reporte mudanças.

## 8. Critérios de Aceite e Validação (*Healthchecks*)
Para que a automação seja considerada finalizada com sucesso, os seguintes comandos devem retornar sem erros:

1. **Idempotência**: uma segunda execução de `ansible-playbook site.yml` termina com `changed=0` em todos os hosts.
2. **Validação do Munge** (em cada nó e entre nós):
   ```bash
   munge -n | unmunge
   munge -n | ssh <outro-nó> unmunge
   ```
   *Resultado esperado*: `STATUS: Success (0)`.
3. **Validação de Nós e Partições no Slurm**:
   ```bash
   sinfo -N -l
   ```
   *Resultado esperado*: Todos os nós listados com estado `IDLE` (disponíveis).
4. **Checagem de Recursos Detectados pelo Slurm**:
   ```bash
   scontrol show node <hostname>
   ```
   *Resultado esperado*: Quantidade correta de CPUs, RealMemory e `Gres=gpu:X` declaradas.
5. **Prioridade e Contabilidade Ativas**:
   ```bash
   scontrol show config | grep -E 'PriorityType|AccountingStorageType|SelectTypeParameters'
   sacctmgr show assoc format=Cluster,Account,User
   sshare -a
   ```
   *Resultado esperado*: `priority/multifactor`, `accounting_storage/slurmdbd`, `CR_Core_Memory`; os cinco usuários associados à conta do laboratório e listados no `sshare`.
6. **Teste de Alocação Real de GPU**:
   ```bash
   srun --gres=gpu:1 nvidia-smi -L
   ```
   *Resultado esperado*: A GPU é listada com sucesso dentro da sessão do job. Em nó com mais de uma GPU, apenas uma é listada (comprova `ConstrainDevices`).
7. **Registro no Histórico**:
   ```bash
   sacct -X --format=JobID,User,Account,State,Elapsed,AllocTRES%40
   ```
   *Resultado esperado*: O job do item 6 aparece com estado `COMPLETED` e `gres/gpu=1` em `AllocTRES`.
8. **NAS Acessível nos Jobs**:
   ```bash
   srun -w <nó> ls /mnt/nas/telemetry
   ```
   *Resultado esperado*: A pasta é listada em cada nó de computação, e um arquivo criado por um usuário em um nó aparece com o mesmo dono nos demais.

## 9. Observações e Limitações

1. **Ceph ainda em avaliação.** Esta spec assume NFS. O Plano de Trabalho mantém Ceph como alternativa até março/2027. A troca afeta apenas a role `nfs_client` e as variáveis `nas`.
2. **Modelo de variáveis diverge do tutorial.** Esta spec descreve o hardware por host (`host_vars/`), adequado a um cluster heterogêneo. O tutorial (apostila) usa uma lista `slurm_nodes` em `group_vars/all.yml`, adequada a uma máquina única. O tutorial pode ser alinhado a este modelo quando chegar às partes de expansão.
3. **Valores de prioridade são iniciais.** Os pesos e a meia-vida da seção 5.1 são pontos de partida. A configuração final deve ser fixada antes dos experimentos da SPEC-03, porque altera diretamente a ordem dos jobs.
4. **`ReturnToService=2`.** Devolve automaticamente ao serviço um nó que se registra com configuração válida, independentemente do motivo pelo qual caiu. É conveniente para o laboratório, mas pode mascarar falhas intermitentes de hardware. Nós que caem repetidamente devem ser investigados pelo log do `slurmctld`.
5. **Comprovação do isolamento de GPU.** `ConstrainDevices` só pode ser comprovado em nó com mais de uma GPU (critério 6). Em nós com uma única GPU, o teste confirma apenas a alocação.
6. **GPUs heterogêneas.** O campo `gpu_type` permite pedir um modelo específico (`--gres=gpu:<tipo>:1`). Se for omitido, o Slurm trata todas as GPUs como equivalentes, e jobs podem cair em GPUs de desempenho diferente (ver SPEC-02, Observação 2).
7. **Detecção automática de GPUs.** O `gres.conf` declara os dispositivos manualmente. O Slurm também oferece `AutoDetect=nvml`, que depende de o pacote do Slurm ter sido compilado com suporte a NVML; a disponibilidade no pacote do Ubuntu deve ser verificada antes de adotá-lo.
8. **Rede e firewall.** Os daemons usam as portas 6817 (`slurmctld`), 6818 (`slurmd`) e 6819 (`slurmdbd`), e o NFS usa a porta 2049. Se houver firewall entre os nós, essas portas devem ser liberadas. A resolução de nomes (`/etc/hosts` ou DNS) também deve permitir que todos os nós se encontrem pelo nome curto.
9. **Acesso aos nós.** O Ansible acessa os nós por SSH com um usuário com `sudo`. A distribuição das chaves SSH de administração é um pré-requisito manual, fora do playbook.
